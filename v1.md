# Polonez Loyalty API v1

This file documents the current v1 behavior of `polonez_loyalty` for POS integrators.

## Base URL

- Primary (Stage): `https://stage.odoo-stage.polonez.dev/odoo`
- Production: `https://erp.tempside.ltd/odoo`
- Swagger UI: `https://shooma.github.io/loyalty-backend-swagger/`

## Endpoints

- `POST /api/v1/loyalty/get-member` (canonical)
- `POST /api/v1/loyalty/finalize-order` (canonical)
- Temporary stage compatibility routes:
  - `POST /odoo/api/v1/loyalty/get-member`
  - `POST /odoo/api/v1/loyalty/finalize-order`

Stage note:
- Stage uses host-based DB selection (`dbfilter = ^%d$`), so use `stage.odoo-stage.polonez.dev`
  for DB `stage`.

## Monetary Units

All monetary fields are sent in minor units, as integers.

- IE shop: `700` = `EUR 7.00`, `1400` = `EUR 14.00`
- NI shop: `700` = `GBP 7.00` (pence)

The currency is that of the shop's operating country (see Operating Country).

## Operating Country (IE / NI)

The loyalty programme runs in two countries — Ireland (`ie`, EUR) and Northern
Ireland (`ni`, GBP). At the till the country is determined by the **shop**
(resolved from `shop_id`), not by the member:

- Points and vouchers belong to the shop's country. A member has an independent
  points wallet per country; `points_balance` / `current_points` reflect the
  wallet for the shop's country.
- A scanned voucher that belongs to the other country is returned not applied
  with `reason_code: WRONG_COUNTRY`.
- The member card code and loyalty QR are country-independent (one identity);
  the same QR works at any shop and points land in that shop's country.
- The member's in-app country choice (mobile `PUT /me/country`) only affects what
  they browse in the app; it never overrides the shop at the till.

## Voucher Code Format

- Clients must treat the code as opaque despite the prefix: the prefix is a
  diagnostic aid for humans reading logs and receipts, never a field to branch
  on, and the random part carries no meaning at all.
- Current format: a semantic prefix, a hyphen, and 16 random characters from
  `A-Z2-9` with `I` and `O` excluded (QR/OCR-safe): `BUY-CZGGAM9QY7R4JYE6`.
- Prefixes: `WEL` (welcome), `BDY` (birthday), `BUY` (x_off_y), `IND`
  (individual), `PTS` (points converted to a voucher).
- Pre-2026 vouchers may still carry the legacy 20-digit numeric code, so do not
  validate the field as numeric, and do not assume a prefix is present.

## Authorization

Use `Authorization: Bearer <token>`.

Token scopes:
- POS-scoped token (`polonez.loyalty.token` linked to POS): `X-Pos-Id` is optional.
- Store-scoped token (`polonez.loyalty.token` linked to shop): `X-Pos-Id` is required.

If `X-Pos-Id` is present and `pos_id` is present in body, they must match.

## Seeded API Tokens

By default, seeds create:

- Store token format: `store-token-<shop_code_lower>`
- POS token format: `pos-token-<shop_code_lower>-<pos_id_lower>`

Examples:

- `store-token-athlo`
- `pos-token-athlo-01`

## Headers

- Required:
  - `Content-Type: application/json`
  - `Authorization: Bearer <token>`
- Conditional:
  - `X-Pos-Id: <pos_id>` is required for store-scoped token and optional for POS-scoped token.

## Response Shape

### get-member

- `status` (bool)
- `member_found` (bool)
- `member_name` (string)
- `points_balance` (integer)
- `discount_total` (integer, cents)
- `scanned_vouchers[]`
- `discounts[]` (only positive discounts)
- `messages[]`

### finalize-order

- `status` (bool)
- `member_found` (bool)
- `member_name` (string)
- `points_collected` (integer)
- `current_points` (integer)
- `scanned_vouchers[]`
- `vouchers[]` (newly issued vouchers for printing/app)
- `messages[]` (receipt-ready lines)

`messages[]` for `finalize-order` is intended for receipt output and includes:

- `Staff total discount: EUR X.XX` (when staff discount is applied)
- `Used vouchers: N` + `Used voucher: <id> (<name>)` for each applied voucher (only when at least one voucher was applied)
- `Accrued vouchers: N` (only when `N > 0`)

## Implemented Validation

- Missing or invalid bearer auth -> `401`.
- Unknown/inactive token -> `401`.
- Token scope mismatch -> `403`.
- Missing `X-Pos-Id` for store token -> `400`.
- `timestamp` format is `YYYY-MM-DD HH:MM:SS`.
- `transaction_value` and `change` are non-negative numbers.
- `vouchers` and `basket_items` are arrays when present.
- `tenders` can be provided optionally; if provided, it should be an array.

## Discount Rules

- Return only discounts with `discount > 0`.
- Voucher and staff discounts are distributed across basket lines proportionally to line value.
- Staff discount (10%) is applied before voucher discounts.
- Voucher eligibility and application are evaluated after staff discount.
- While evaluating multiple vouchers, backend applies vouchers from higher threshold to lower
  and decreases the remaining eligibility base after each applied voucher.

## Voucher Issuance Rules

- `finalize-order` is idempotent by `transaction_id`.
- Vouchers are auto-issued from active `x_off_y` rules. Each rule targets an
  **audience** — `anonymous`, `registered`, or `both` — so an anonymous
  (unidentified) transaction only triggers rules whose audience includes
  anonymous, and an identified member only triggers rules whose audience
  includes registered:
  - rules are checked from bigger purchase threshold to smaller
  - one transaction may issue multiple vouchers
  - after each issued voucher, remaining amount is reduced by rule trigger threshold
  - optional store filter applies when rule has selected stores
- There is **no separate "anonymous welcome" issuance**. The welcome voucher is
  granted only to members on mobile sign-up (see the Mobile API); an anonymous
  spend-threshold voucher is simply an `x_off_y` rule with `audience = anonymous`.
- Issued voucher payload field is `printed`:
  - `printed = true` for anonymous issuance (print on receipt)
  - `printed = false` for identified members (available later in mobile app)

## Member Verification and Points

- `not_verified` member: only mandatory profile data (`name`, `phone`, generated card code)
- `verified` member: `email`, `phone`, `name`, `surname`, `birthday`, `nationality` are all filled
- Only `verified` members accrue loyalty points on `finalize-order`

Default seeded rules (amounts in cents):
- `5 off 25` — audience `anonymous`, trigger `2500`, applicability threshold `2500`, discount `500`, valid `14` days
- `5 off 25` — audience `registered`, trigger `2500`, applicability threshold `2500`, discount `500`, valid `365` days
- `10 off 50` — audience `registered`, trigger `5000`, applicability threshold `5000`, discount `1000`, valid `365` days

## Validity Rules

Each `x_off_y` rule carries its own start offset (`valid_from_offset_days`,
default `1`) and lifetime (`validity_days`), configured in
`Loyalty -> Voucher Rules`. The issued voucher activates that many days after
issuance and stays valid for its lifetime.

Voucher types and default windows:

- `Welcome` (member, mobile sign-up): active immediately, lifetime `14` days
- `Birthday` (personal): member must have birthday, active from `7` days before birthday until `7` days after
- `x_off_y` (member or anonymous, per rule): default start `+1` day, lifetime per rule
- `Individual` (personal): starts on issue day, lifetime `30` days

Legacy compatibility:
- `Standard` is normalized to `x_off_y`
